2. 개인 메모 CRUD는 `/api/notes`의 로그인·소유자 검사와 DB RLS를 사용합니다.
3. 원본 메모 API 직접 접근 차단은 5단계 기록의 학생 실제 확인 결과로 보존합니다.

## 요청 계약 확인

[판정 요청·응답 계약](../docs/DECIDER_REQUEST.md)을 읽었습니다.

- 사용자: `request.subjectId`는 엔진이 확인한 가명 주체 ID입니다. Supabase 사용자 번호와 직접 비교하지 않습니다.
- 기기 등록: `request.deviceRegistered`는 엔진이 전달하는 등록 여부입니다. `deviceId`는 확인된 기기 ID이며 개인키가 아닙니다.
- 실제 릴레이는 미등록 기기를 판정기 이전에 차단합니다. `false` 요청의 로컬 연습은 실제 접속·심판 판정 증거가 아닙니다.
- 함수 `decide(request)`와 응답의 다섯 항목은 유지합니다. 계약에 없는 신원·기기·역할 객체를 만들지 않습니다.

## 제작 1~3 완료 (2026-10-13)

사용자의 「만들기를 쭉 진행」 요청에 따라 제작 1~3을 진행했습니다.
위 준비 당시 기본 거부·미실행 기록은 아래 실제 구현·시험 결과로 갱신됩니다.

- 제작 1: 계약의 `subjectId`와 `deviceRegistered` 설명을 확인했습니다. 새 인증서·CA·키 파일은 만들지 않았습니다.
- 제작 2: `src/decider.mjs`에서 `deviceRegistered === true`일 때만 `allow`·`approved`를 반환합니다.
  미등록·등록 값 누락은 `deny`·`device_not_registered`입니다. RULE_IDS는 실제 구현한 `device_registered`만 남겼습니다.
  시작용 `starter.deny`를 교체했으며 추가 보안 규칙·요청 필드는 만들지 않았습니다.
  `decide(request)`와 응답 다섯 항목은 유지했습니다.
- 제작 3: `npm.cmd run decider:test`를 실제 실행해 아래 두 건이 통과했습니다.
  루트 README에 재실행 순서와 정상·거부 결과를 기록했습니다.

```text
통과 · 등록 기기의 정상 요청
통과 · 미등록 기기의 가상 요청
이 명령은 가상 요청으로 연습하며 심판 통과 증거가 아닙니다.
```

별도 Node 가상 확인은 실제 판정기를 호출해 응답 다섯 항목·schema·requestId·규칙 이름도 검증했습니다.

| 등록 값 | 판정 | 이유 코드 |
| --- | --- | --- |
| `true` | `allow` | `approved` |

| 숫자 `1` | `deny` | `device_not_registered` |

이번 제작 변경 파일은 `src/decider.mjs`, 루트 `README.md`, `TODO.md`, `6/README.md`입니다.

## 추가 공격 점검·가상 시험 보강 (2026-10-13)

학생이 지정한 네 공격의 검사 지점을 요청 계약·로그인 검증·메모 API·배포 설정과 대조했습니다.
현재 자료실 주소는 일반 HTTPS이며 mTLS 통로·기기 등록부·기기와 사용자 연결 검사는 이 저장소에 없습니다.
현재 메모 API는 토큰 검증과 소유자 검사를 수행하지만 `src/decider.mjs`를 호출하지 않습니다.

| 요청한 공격 | 실제 확인 결과 | 남은 조치 |
| --- | --- | --- |
| 미등록 기기 인증서로 조회 | 실제 클라이언트 인증서 시험 미실행. 현재 인증서 등록부 검사 없음 | 공식 mTLS 통로·등록부 연결 후 미등록 인증서 거부 확인 |
| 클라이언트 인증서 없이 mTLS 통로 요청 | 현재 주소에 인증서 없는 HTTPS 읽기 요청을 실제 전송. TLS 성공, `/` 200·`/api/notes` 401 | mTLS 입구 구현 또는 운영 통로 연결 후 인증서 없는 요청을 메모 처리 전에 거부 |
| 등록 기기와 다른 사용자 토큰 조합 | 실제 조합 시험 미실행. 동일한 가상 deviceId에 subjectId만 바꾼 직접 판정 호출은 둘 다 allow | 엔진의 사용자·기기 연결 검증과 실제 조합 시험 필요 |
| 미등록 가상 기기 사건을 판정기에 직접 입력 | `deviceRegistered: false`와 별도 가상 deviceId를 직접 입력해 deny·device_not_registered 확인 | 로컬 거부 확인 완료. 심판 판정은 별도 |

인증서 없는 요청의 401은 로그인 토큰이 없어서 거부된 결과이며 TLS 단계의 mTLS 거부가 아닙니다.
가상 subjectId 변경 시험은 실제 토큰·인증서 조합 시험이 아닙니다. 판정기는 true라는 값 자체의 출처나 사용자 연결을 검증하지 않습니다.
등록된 가명 subjectId와 Supabase 사용자 번호를 임의로 직접 비교하는 규칙을 만들지 않았습니다.

- 등록 값 누락
- 문자열 `"true"`, 숫자 `1`, `null` 등록 값
- 별도 미등록 가상 기기 사건 직접 입력
- 추가 인증을 마친 미등록 기기

실제 mTLS와 사용자·기기 연결은 미완료이며 이 기록을 해당 세 공격의 차단 완료로 해석하지 않습니다.
이전의 Vercel 로그인으로 등록 기기를 확인할 수 있다는 안내는 정정합니다.

기술 근거: [Vercel CDN 처리 흐름](https://vercel.com/docs/how-vercel-cdn-works)은 애플리케이션 코드 전에 플랫폼에서 TLS를 종료한다고 설명합니다.
따라서 현재 함수에 등록 여부 플래그를 추가하는 것만으로 TLS의 클라이언트 인증서 요구를 구현했다고 할 수 없습니다.
[RFC 8705](https://www.rfc-editor.org/rfc/rfc8705.html)는 클라이언트 인증서 검증과 인증서에 묶인 접근 토큰을 별도 보안 기제로 설명합니다.
실제 TLS 입구·등록부·신뢰할 수 있는 사용자 연결 계약과 직접 주소 우회 차단이 필요합니다.
