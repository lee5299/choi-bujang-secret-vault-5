# 8단계 DB·운영 권한표 설정 안내

코드는 작성했지만 새 공지 테이블·강사 지정·운영 엔진 권한표를 실제 설정한 상태는 아닙니다.
아래 작업은 학생과 운영 관리자가 공식 설정 화면에서 진행합니다. 실제 ID·키·토큰·공지 본문을 채팅이나 Git에 넣지 마세요.

## 1. 공지 저장소 만들기

Supabase 프로젝트 → **SQL Editor → New query**에서
[공지 준비 SQL](../docs/sql/stage8-announcements-apply.sql)을 읽고 전체를 Run합니다.
이 SQL은 `library_announcements`, `library_instructors`와 서버 전용 접근 함수를 만듭니다.
기존 `library_notes`·메모 UUID·메모 본문·주소를 옮기거나 바꾸지 않습니다.
새 테이블에 가상 공지나 실제 사용자 행을 자동으로 넣지 않습니다.

그다음 [권한 조회 SQL](../docs/sql/stage8-announcements-audit.sql)을 Run합니다.
정상 결과는 두 테이블의 RLS true, anon·학생의 테이블/열 직접 접근 false,
서버 읽기 true, anon_rpc·student_rpc false, server_rpc true입니다.
오류가 나면 `ROLLBACK;` 후 첫 오류만 확인합니다. 이번 작업에서는 실제 DB에 SQL을 실행하지 않았습니다.

## 2. 강사는 관리자가 지정

Supabase **Authentication → Users**에서 강사로 승인한 계정을 확인합니다.
프로젝트 관리자만 **Table Editor → library_instructors → Insert row**에서 해당 사용자 UUID를
`user_id`에 넣고 `active`를 true로 지정합니다. 실제 값은 공식 화면 안에서만 다룹니다.
학생의 `user_metadata.role`, 요청 본문·쿼리의 `role`, 심판 계정 표시는 강사 지정 근거가 아닙니다.
강사 권한을 회수하려면 같은 행의 `active`를 false로 변경합니다.

권장 정책은 이 자료실에 로그인한 사용자의 공지 읽기, 활성 강사의 공지 추가,
활성 강사 자신의 공지 수정·삭제입니다. 다른 강사의 공지 수정은 404, 일반 학생의 공지 쓰기는 403입니다.
기존 공지 저장소가 확인되지 않아 별도 저장소를 만들었으며 기존 메모를 공지로 변환하지 않았습니다.
학습 자료실 하나를 공지 공유 범위로 잡았습니다. 반별 공지 분리가 필요하면 공식 반 소속 검증과 별도 정책이 필요합니다.

## 3. 운영 엔진의 권한표 설정

판정 요청의 18개 필드는 바꾸지 않았습니다. 서버 전용 환경변수 `ALEPH_RESOURCE_POLICY_JSON`을 권한표 저장 위치로 새로 정의했습니다.
[빈 양식](../docs/stage8-resource-policy.template.json)은 설명용입니다. 꺾쇠 자리표시자가 있는 상태에서는 권한이 부여되지 않습니다.
완성된 권한표는 운영 엔진이 학생 `decide(request)`를 실행하는 서버의 공식 비밀 설정란에 관리자가 넣습니다.
그 서버가 Vercel과 다르면 Vercel 환경변수만 설정해도 운영 판정기에 전달되지 않습니다.
실제 입력값을 파일로 저장·커밋하거나 채팅에 붙여 넣지 않습니다. 코드에 키를 넣지 않습니다.

| 필드 | 공식 근거와 설정 방법 |
| --- | --- |
| `classId`, `projectId`, `service` | 엔진이 확인한 반·프로젝트·서비스와 정확히 일치해야 합니다. |
| `policyRevision` | 현재 엔진 정책 버전과 같은 양의 정수입니다. 양식의 1을 운영 버전이라고 가정하지 않습니다. |
| `expiresAt` | 관리자가 정한 만료 UTC ISO 시각입니다. 만료되면 모두 거부합니다. |
| `denyReasonCode` | 운영 등록부의 allowedReasonCodes에서 자원 권한 거부용으로 등록된 코드를 사용합니다. 새 코드의 등록 여부를 추측하지 않습니다. |
| `grants[].subjectId` | 운영 엔진이 발급자·대상·반·프로젝트를 검증해 만든 가명 사용자입니다. Supabase UUID를 그대로 넣거나 변환 규칙을 추측하지 않습니다. |
| `grants[].deviceId` | 그 사용자에게 연결된 검증된 기기의 16자리 소문자 16진수 ID입니다. 개인키가 아닙니다. |
| `grants[].method` | 실제 허용할 GET·POST·PUT·DELETE 중 하나입니다. 동작별로 별도 행을 둡니다. |
| `grants[].path` | 해당 사용자 소유 자료나 승인된 공지의 정확한 경로입니다. 와일드카드·export·쿼리·후행 슬래시는 허용하지 않습니다. |

관리자는 **저장된 메모 소유자와 검증된 가명 사용자의 연결을 확인한 뒤** 그 사용자의 메모 경로만 권한표에 추가합니다.
`GET /api/notes`, `POST /api/notes`는 로그인한 사용자의 소유자 제한 목록·추가용으로 따로 등록하고,
각 자기 메모의 GET·PUT·DELETE를 UUID가 포함된 정확한 경로로 등록합니다.
강사의 공지 쓰기 권한도 강사 승인 확인 뒤에만 등록합니다. 학생에게 공지 PUT·POST·DELETE를 등록하지 않습니다.
같은 사용자라도 새 기기에는 별도 승인 행이 필요합니다. 공개 권한표에 실제 신원·소유자 정보를 노출하지 않습니다.

운영 엔진이 `/notes/...`를 전달한다면 그 경로를, `/api/notes/...`를 전달한다면 그 경로를 그대로 등록합니다.
코드는 두 경로 모양을 인식하지만 한 경로의 권한을 다른 접두사 경로로 확대하지 않습니다.
쿼리 원문은 계약에 없어 판정기는 `queryLength > 0` 요청을 거부합니다. 자료 선택은 UUID 경로로 합니다.
새 메모를 만들면 새 UUID의 허용 행을 권한표에 추가해야 합니다. 이 자동 동기화는 현재 운영 계약에 없어 구현하지 않았습니다.

권한표가 없거나 깨졌으면 판정기는 `deny`와 기존 `step_up_required` 코드·`resource_scope` 규칙을 반환합니다.
이는 추가 인증만 하면 허용한다는 뜻이 아닙니다. 유효한 권한표가 있어야 하고 재확인으로 구역 권한을 우회할 수 없습니다.
유효한 권한표에서의 권한 거부는 운영자가 등록한 `denyReasonCode`를 사용합니다.
시험의 `resource_forbidden`은 가상 시험 설정일 뿐 운영 코드 등록의 증거가 아닙니다.

## 4. 배포와 직접 확인

Vercel **프로젝트 → Settings → Environment Variables**에서 기존 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`를 유지합니다.
공지 API도 같은 서버 비밀 설정을 사용합니다. 별도 브라우저 키·학생 role 입력란은 만들지 않았습니다.
저장점 코드를 GitHub에 올려 새 배포를 만든 뒤 `/aleph.json`의 단계 8·배포 커밋 일치를 확인합니다.
이번 요청에는 원격 업로드·실제 DB 적용·운영 권한표 입력을 수행하지 않았습니다.

로컬 확인 명령: `npm.cmd run test:stage8`.
파일 목록에서 **8 → README.md**와 **8 → 권한설정.md**를 누릅니다.
배포된 메모 화면에서는 로그인 후 **추가 → 수정 → 삭제**로 기존 본인 메모 기능을 확인합니다.
브라우저 개발자 도구 **Network → /api/notes 요청 → Preview / Headers**에서 `resourceId`·`X-Resource-Id`를 확인합니다.
공지 API는 `/api/announcements`와 `/api/announcements/:id`이며 화면 메뉴를 추가하지 않았습니다.
토큰을 콘솔·채팅·로그에 붙여 넣지 말고 로그인 세션을 사용하는 승인된 API 시험 환경에서 확인합니다.

정상 기준: A의 자기 메모 CRUD, 로그인한 사용자의 공지 읽기, 승인된 강사의 자기 공지 쓰기.
거부 기준: 무로그인 401, B의 A 메모 404·목록에서 미노출, 학생의 공지 쓰기 403,
다른 강사의 공지 쓰기 404, 판정기에서 미승인 사용자·기기·동작·경로 deny.
로컬 시험의 Auth·DB·운영 권한표는 모두 가상이며 실제 운영 연결을 대신하지 않습니다.

## 모호한 부분과 이번 선택

1. 운영 subjectId와 Supabase UUID의 연결 방법이 없습니다. 관리자가 공식 연결 근거로 권한을 등록하도록 했고 자동 매핑을 만들지 않았습니다.
2. 엔진이 학생 판정기를 어떤 서버·환경에서 실행하는지 확인되지 않았습니다. 환경변수 전달 방법은 운영 측이 확인해야 합니다.
3. 새 자원 거부 이유 코드 등록부를 읽을 수 없습니다. 새 코드 대신 권한표에서 등록된 코드를 지정하도록 했습니다.
4. 강사 공지 저장소와 반별 범위가 없었습니다. 별도 공지 저장소·관리자 강사 지정·자료실 내 로그인 사용자 읽기를 권장 기본값으로 구현했습니다.
5. 메모 API는 여전히 판정기를 직접 호출하지 않습니다. 구역별 엔진 판정과 API의 소유자·강사 검사 두 층을 작성했으며 운영 릴레이 연결은 확인되지 않았습니다.
6. 권한표는 한 반·프로젝트·서비스·정책 버전에 묶인 정확한 경로 목록입니다. 자료 생성·삭제·기기 변경 후 자동 동기화와 여러 서비스 정책 배포는 운영 연결이 필요합니다.

위 항목은 실제 시험·심판 판정·배포 완료로 보고하지 않습니다.
