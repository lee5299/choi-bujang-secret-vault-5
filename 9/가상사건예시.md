# 9단계 연습용 가상 사건

2026-10-13, 사용자의 연습용 데이터 작성 요청에 따라 만들었습니다.
실제 계정·이메일·비밀번호·토큰·개인키·메모 본문을 포함하지 않습니다.
가명 사용자와 기기 번호는 모두 이 연습을 위해 만든 값입니다.
자료 파일은 [stage9-events-proposal.json](../test/fixtures/stage9-events-proposal.json)입니다.

## 두 종류의 자료

| JSON 위치 | 내용 | 사용 범위 |
| --- | --- | --- |
| localContract.cases | 현재 탐지 계약의 at·method·identity.sub만 있는 실제 사건 배열 6개 | 각 cases 항목의 events를 현재 detect(events)에 전달할 수 있음 |
| compoundProposal.cases | 기기·판정·네트워크를 포함한 학생 제안 사건 배열 9개 | 원문 요구를 설명하고 검토하는 초안. 현재 detect에는 연결하지 않았음 |

이 자료의 모든 expected는 기대 결과입니다. 이번에는 새 자료로 탐지 시험을 실행하지 않았으며 모든 verification은 not_run입니다.
현재 코드의 이전 시험 221개·연습 6건 통과 기록을 이 새 자료의 실행 결과로 사용하지 않습니다.

## 현재 계약의 예시

```json
{
  "at": "2026-10-01T00:00:00.000Z",
  "method": "GET",
  "identity": { "sub": "learner_fixture" }
}
```

자료에는 count 요약 대신 시각이 있는 사건을 실제 건수만큼 생성했습니다.
예를 들어 L03의 events는 2초 간격의 조회 121건입니다.

| ID | 상황 | 현재 계약 기대 결과 |
| --- | --- | --- |
| L01 | 정상 조회 30건 | observe |
| L02 | 10분 안에 정확히 120건 | observe |
| L03 | 10분 안에 121건 | propose_revocation·burst_read·가명 사용자 |
| L04 | 10분 안에 200건 | propose_revocation·burst_read·가명 사용자 |
| L05 | 다른 사용자 각각 100건 | observe |
| L06 | 7초 간격으로 흩어진 조회 200건 | observe |

## 네트워크·기기를 포함한 학생 제안 예시

아래는 **직접 만든 학생 제안 형식이며 공식 엔진 형식이 아닙니다.**
docs/DETECT_EVENTS.md나 docs/DECIDER_REQUEST.md의 계약을 변경하지 않았습니다.

```json
{
  "at": "2026-10-01T00:00:00.000Z",
  "method": "GET",
  "identity": { "sub": "learner_fixture" },
  "deviceId": "1111111111111111",
  "decision": "allow",
  "signals": {
    "source": "student_fixture",
    "network": "unusual"
  }
}
```

| 항목 | 이 연습에서의 뜻 |
| --- | --- |
| identity.sub | 가명 사용자. 실제 로그인 계정 ID와 연결하지 않음 |
| deviceId | 가상 기기 번호. 111…은 기기 A, 222…는 기기 B. 개인키 아님 |
| method·decision | 요청 종류와 가상 접속 판정 |
| signals.source | student_fixture: 학생이 만든 연습 데이터임을 표시 |
| signals.network | usual: 평소 네트워크, unusual: 다른 네트워크, unknown: 확인 불가 |
| at | 사건 시각. 조회 창 계산에 사용 |

연습 가정은 사용자+기기별 허용된 GET 조회를 어느 10분 창에서든 120건 초과 집계하고,
그 창 안에 같은 기기의 unusual 네트워크 신호가 있을 때만 해당 기기 한 개를 제안하는 것입니다.
10분·120건 기준은 기존 로컬 연습에서 가져온 초안 값이며 원문 복합 조건의 공식 기준으로 확인하지 않았습니다.
unknown은 정상 네트워크로 추정하지 않으며 이 연습에서는 회수 제안을 내지 않습니다.
다른 네트워크나 지역 하나만으로 회수를 제안하지 않습니다.

| ID | 상황 | 학생 제안 기대 결과 |
| --- | --- | --- |
| P01 | 평소 네트워크·정상 조회 30건 | observe |
| P02 | 다른 네트워크·조회 30건 | observe |
| P03 | 평소 네트워크·조회 121건 | observe |
| P04 | 다른 네트워크·조회 121건 | 기기 A만 제안 |
| P05 | 같은 사용자의 기기 A·B가 각각 100건 조회 | observe. 두 기기를 합산하지 않음 |
| P06 | 기기 A는 다른 네트워크에서 121건, 기기 B는 정상 30건 | 기기 A만 제안, 기기 B 유지 |
| P07 | 네트워크 확인 불가·조회 121건 | observe. 네트워크를 임의로 보정하지 않음 |
| P08 | 다른 네트워크·정확히 120건 | observe |
| P09 | 다른 네트워크·창 밖으로 흩어진 200건 | observe |

P04·P06의 기대 제안은 아래 초안입니다. 이유 코드와 deviceId 출력 필드도 공식 승인 전의 학생 제안입니다.

```json
{
  "action": "propose_revocation",
  "reasonCode": "compound_read_anomaly",
  "subject": "learner_fixture",
  "deviceId": "1111111111111111"
}
```

이 예시는 대상과 이유를 설명합니다. 실제 기기 권한 변경·접속 회수·심판 시간 측정을 수행하지 않습니다.
현재 detect는 기기·네트워크 추가 필드를 읽지 않으므로 P03 같은 사례를 넣으면 위 기대와 다른 결과가 나옵니다.
compoundProposal 자료를 현재 함수의 공식 시험 입력으로 사용하지 않습니다.

## 확인 방법

프로젝트 루트에서 아래 명령을 실행하거나 파일 목록 **9 → 가상사건예시.md**를 누릅니다.

```powershell
Invoke-Item '9/가상사건예시.md'
```

원본 데이터는 **test → fixtures → stage9-events-proposal.json**에서 봅니다.
정상 기대는 P01·P02·P03·P05·P07~P09의 observe, 의심 기대는 P04·P06의 기기 A 한 개 제안입니다.
실제 접속 거부는 이 자료의 결과가 아닙니다. 이번 작업은 자료 작성과 JSON 형식 확인이며 탐지 코드·설정·배포는 변경하지 않았습니다.
