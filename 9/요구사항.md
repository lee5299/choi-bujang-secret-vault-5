M1·N1의 탐지·회수 제안은 학생 제작 범위입니다. M2~M4의 실제 회수 뒤 거부는 심판 확인 항목이며 9단계 학생 제작 완료 조건이 아닙니다.
M2~M4를 이유로 decide에 회수 상태 검사를 추가하거나 회수 API·기기 권한 변경을 구현하지 않습니다.
원문은 첫 의심 요청의 즉시 deny를 요구하지 않습니다. 회수 집행 전 사건을 임의로 접속 거부로 바꾸지 않습니다.
표의 후보 사유·규칙은 검토용 이름이며 현재 RULE_IDS·운영 등록·학생 구현에 반영하지 않았습니다.

M1·N1의 중복 처리 설계 후보(R4): 같은 확인된 대상 기기에 동일 제안이 반복되면 최초 제안만 유효하게 취급합니다.
이는 원문에 없는 추가 제안입니다. 동일 배치·조회 창·실행 간 중복 범위와 다시 제안할 조건은 미확정이며,
영구적으로 제안 1건만 허용하거나 임의 전역 상태를 두는 구현으로 확정하지 않습니다.
첫 의심 시각은 공식 입력·출력 계약이 제공할 때만 보존합니다. 심판 측 경과 시간 측정을 대신하거나 응답 필드를 임의 추가하지 않습니다.

탐지는 사건 범주를, 판정기는 자원 구역을 다룹니다. 새 탐지 범주 이름은 설계 후보입니다.

기존 RULE_IDS는 `device_registered`, `step_up_required`, `resource_scope`, `announcement_zone`, `instructor_material_zone` 다섯 개입니다.
허용 응답에도 기기·구역 규칙과 기존 신호 검사가 적용됩니다. 탐지 제안은 접속 응답에 추가하지 않습니다.

## allowedRoutes 후보

9단계 원문에는 새 자원 경로 요청이 없습니다. 현재 판정기 구역의 허용 경로에 맞춘 아래 6개를 유지하는 후보입니다.
실제 설정은 변경하지 않았습니다. `/api` 없는 표기는 판정 계약의 기존 경로 표기로 처리하며 등록 경로를 중복 추가하지 않습니다.

```text
POST /api/notes
GET /api/notes/:id
PUT /api/notes/:id
DELETE /api/notes/:id
GET /api/announcements
GET /api/announcements/:id
```

GET /api/notes 전체 목록, 공지 쓰기, 강사 자료, export·검색 등 기능 경로, 회수 API는 이 후보에 포함하지 않습니다.
자료 API가 제공하는 직접 화면 기능과 판정기의 등록 경로를 구분합니다. 타인 메모 접근은 API가 저장된 소유자로 거부합니다.

제작 1의 확인 조건인 "정상·의심 사건을 비밀값 없이 읽을 수 있어야"에 대응하는 행이 없습니다. 다음 행을 추가해 주세요. 입력 사건에 메모 본문·토큰·실명 같은 추가 필드를 넣었을 때, 탐지 결과·로그·저장소·`npm run bundle` 출력 어디에도 그 값이 나오지 않아야 하고, 읽는 필드는 허용 목록으로 제한합니다.

**R3. decide 응답 불변 회귀 행 누락**

계약 대조 표에는 “decide 다섯 항목 유지”가 있지만 시험으로 옮길 행이 없습니다. 의심 사건과 같은 요청을 decide에 넣어도 응답 키가 `schema·requestId·decision·reasonCode·ruleIds` 다섯 개 그대로이고 탐지 필드가 섞이지 않는지 확인하는 행(N6)을 추가해 주세요.

**R4. 제안 중복 처리 미정 (M1·N1)**

다량 조회가 계속되면 사건마다 제안이 반복될 수 있습니다. "기기 한 개로 한정"과 맞추려면 **같은 대상 기기에는 제안 1건**(또는 첫 제안만 유효)이라는 기대를 표에 적어 두는 것이 좋습니다. 첫 의심 시점을 남겨 두면 심판의 경과 시간 측정과도 어긋나지 않습니다.

**R5. 집계 단위 명시 (N5, 계약 대조 표 「복합 조건」 행)**

현재 로컬 연습은 `identity.sub`, 즉 사용자 단위로 셉니다. 안내의 대상은 기기 한 개이므로 집계 단위를 **사용자+기기**로 해야 같은 사용자의 정상 기기가 함께 걸리지 않습니다. 이 내용이 N5 결론에만 암시되어 있으니 복합 조건 행에도 명시해 주세요.

**R6. 질문 목록 우선순위 (Q1~Q7)**

질문 7개가 모두 같은 무게로 적혀 있어 "공식 답이 올 때까지 제작 보류"로 읽힐 수 있습니다. 다음처럼 나눠 주세요.

- **제작 차단**: Q1(사건 필드), Q2(네트워크 판별값·창·임계값), Q7(burst_read와 복합 조건의 관계)
- **제작 비차단·심판 측**: Q5(집행 경로), Q6(시간 측정 기준). 우리 코드가 다루지 않는 영역입니다.
- **차단 질문에 대한 기본값**: Q3·Q4는 Q1의 답에 따라 정해집니다.

**R7. 제작 전 확인: 외부 질문보다 저장소부터 확인**

"기기·네트워크·판정 미제공"은 `docs/DETECT_EVENTS.md` 문서만 보고 내린 결론으로 보입니다. 제작 1이 "제공된 가상 사건"이라고 했으니, 저장소에 사건 예시 파일(fixture·샘플 JSON·`scripts/detect-test.mjs` 안의 생성 데이터)이 있는지와 실제로 어떤 필드가 들어 있는지를 먼저 확인해 주세요. 네트워크·기기 필드가 실제 예시에 있으면 Q1·Q2·Q3의 상당 부분이 저장소 안에서 풀립니다.

정말 없다면 Q7이 핵심입니다. 안내의 "평소와 다른 네트워크 + 다량 조회" 복합 조건과 로컬 `burst_read`(다량 조회 단독으로 제안)는 N4에서 정면으로 충돌합니다. 어느 쪽을 따를지 사용자 결정을 받은 뒤 제작 2를 시작해야 합니다.

**확인 결과 문제 없음**
