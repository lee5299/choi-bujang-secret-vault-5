## 기록 관리 규칙

`data.json`과 `public/data.json`은 메모 본문이 Git 변경 기록에 남지 않도록 추적·제출 대상에서 제외합니다.
이 두 경로를 전체 이력에서 제거하고 `.gitignore`에 등록한 저장점의 검증·적용 안내는
[Git 기록 정리](docs/GIT_HISTORY_CLEANUP.md)에 있습니다. 기존 메모 CRUD는 서버 API와 DB를 계속 사용합니다.

16단계까지 현재 기능·실행 방법·단계별 목차는 이 README에서 관리합니다.
앞으로 할 목표와 미반영·미확인 항목은 루트 `TODO.md`에만 관리합니다.
각 단계의 `숫자/README.md`에는 완료한 작업의 목표·변경 파일과 이유·실제 적용 및 검증 결과·저장점 커밋을 기록합니다.
코드 작성, DB 적용, 배포, 시험은 각각 수행한 사실만 기록합니다.
미실행 항목은 검증 범위의 한계로 명시하고 후속 할 일은 TODO로 연결합니다.
완료한 목표는 TODO에서 제거하고 해당 단계 기록으로 옮깁니다.
나중에 기능이 바뀌면 현재 README를 갱신하고 새 단계 기록에서 이전 단계와 연결합니다.
프로그램 사본은 단계 폴더에 만들지 않습니다. 실행할 SQL·시험 파일은 기록에서 링크합니다.
비밀값·실명·메모 본문은 기록하지 않습니다.

## 실행과 확인

배포 주소: https://choi-bujang-secret-vault-5.vercel.app

```powershell
npm.cmd run build -- --local
```

이 명령은 정적 빌드 확인입니다. 서버 API·실제 DB·배포 확인을 대신하지 않습니다.
가상 시험은 `node --test test/*.test.mjs`입니다.
서버 환경변수는 Vercel의 **프로젝트 → Settings → Environment Variables** 비밀 입력란에서
`SUPABASE_URL`과 `SUPABASE_SECRET_KEY`를 설정합니다. 값 자체를 코드나 기록에 적지 않습니다.
Auth에는 서버의 기존 키를 사용합니다. 별도 공개 키를 사용하려면 서버 전용 환경변수
`SUPABASE_PUBLISHABLE_KEY`를 같은 비밀 입력란에 설정합니다. 브라우저로 전달하지 않습니다.

DB 적용 순서: Supabase **SQL Editor → New query**에서 [5단계 권한 조회](docs/sql/stage5-library-notes-audit.sql)를 실행해 결과를 보관합니다.
그다음 [권한 회수 SQL](docs/sql/stage5-library-notes-apply.sql)을 검토한 후 전체를 Run하고 같은 조회를 반복합니다.
anon·authenticated 권한은 모두 false, PUBLIC·열 ACL 결과는 없음, 서버용 CRUD는 모두 true여야 합니다.
기존 소유자 정책과 RLS는 유지합니다. 오류 시 `ROLLBACK;` 후 첫 오류를 확인합니다.

배포 화면에서 로그인 후 메모 **추가 → 수정 → 삭제**를 누릅니다.
정상 예상: 본인 메모 CRUD. 거부 예상: 무로그인 401, 상대 메모 읽기·수정·삭제 404,
소유자 변경 본문 400, 기존 ID 덮어쓰기 409. `/data.json`은 404여야 합니다.
실제 DB 적용은 학생이 수행했고 전후 조회 화면을 확인했습니다. 배포 점검과 계정 시험 결과는 5단계 기록에 있습니다.

로컬 설정은 11단계 제작 2입니다. 기존 배포 주소·발급자·원본 API·메모/공지/복구 경로를 유지합니다. 신규 기기 SQL은 실제 적용했습니다. 마지막 검토 반영과 배포를 완료했습니다. 실제 기기 인증은 후속 확인 대상입니다. 공개 연결 정보는 access-app.config.json → /access-app.json 및 배포 /aleph.json의 accessApp에 반영합니다. 세션은 메모리에만 두므로 새로고침 뒤 재로그인·기기 확인합니다.
7단계 저장점 `b346b2c` 업로드 뒤 `/aleph.json`의 단계 7·커밋 일치를 실제 HTTP로 확인했습니다.
`originalApiUrl`은 원본 메모 테이블의 쿼리 없는 HTTPS 주소입니다. `judgeIssuer`는 운영 측 설정을 유지합니다.
5단계 당시 배포된 `/aleph.json`의 단계·허용 경로·커밋과 첫 화면 보안 헤더를 실제 HTTP로 확인했습니다.

## 7단계 평소와 다른 접속은 다시 확인합니다

아래는 7단계 당시 구현·검증 기록입니다. 현재 추가된 자원 권한 조건은 8단계 안내를 따릅니다.

판정기 입력은 계약의 `signals`와 `recentEvents`만 사용합니다. 클라이언트 헤더는 읽지 않고
누락·잘못된 형식·알 수 없는 출처를 정상값으로 채우지 않습니다. 이런 입력은 `step_up`·`step_up_required`입니다.
명시된 `source: "none"`·`region/network: "unknown"`은 접속 신호가 없는 상태로 구분하고 기존 기기 조건으로 판정합니다.

로그인한 본인이 자기 메모 ID로 호출합니다. 요청 본문은 읽지 않습니다. 메모가 처음 추가될 때 DB가 봉인 사본을 한 번만 저장하고,
수정·삭제·같은 ID 재추가는 사본을 바꾸지 않습니다. 복구 때 사본 지문을 다시 계산해 대조하고, 복구한 메모를 다시 읽어 ID·소유자·내용 지문이 사본과 같은지 확인합니다.
응답은 `{ id, resourceId, status: restored|recreated|already_matching, changed, verified: { id, owner, contentHash } }`이며 제목·본문·소유자 값은 담지 않습니다.
거부: 무로그인 401, 사본 없음·타인 메모 404 `backup_not_found_or_not_owner`, 사본 검증 실패 503 `backup_integrity_failed`, 같은 ID의 다른 소유자 행 409 `restore_conflict`, 다른 동작 405.
사본·감사 테이블은 추가 전용이며 서버 키도 직접 읽거나 쓰지 못합니다. 다른 메모와 기존 감사 기록은 바꾸지 않습니다.

DB 적용 순서(학생이 직접 실행): Supabase **SQL Editor → New query**에서 조회 SQL을 실행해 결과를 보관 → 적용 SQL을 검토 후 전체 Run →
연습 SQL 전체 Run(오류 메시지의 `DRILL_RESULT all_passed=t`가 통과, 블록 전체가 자동 취소되어 흔적 없음) → 조회 SQL을 다시 실행합니다.

### 공개 작전실 B와 보존한 관리자 기능

현재 사용 화면은 로그인 없는 공개 작전실 B입니다. 사용자 요청으로 관리자 A 메뉴와 전용 로그인 화면은 주석 처리했으며, A 전용 HTML·JS는 배포 정적 파일에서 제외합니다. 주석 원본은 저장소에 보존하므로 저장소 열람자에게 비밀인 정보는 넣지 않습니다.

관리자 요약 API·관리자 판별·기기 서명·기기 승인/회수 기능은 유지합니다. 공개 B에는 관리자 권한이나 사용자·기기별 보호 정보를 추가하지 않습니다. 기존 /operations-room은 보호 API의 진입 확인 기능을 보존하지만 전용 로그인 화면은 배포되지 않습니다.
