# 가상 자료실

현재 로컬 코드는 5단계 자료실에 6단계 기기 등록과 7단계 가상 복합 이상 판정 규칙을 추가한 구현입니다.
로컬·공개 배포 설정은 7단계입니다. 저장점·배포·제출 묶음의 실제 확인 결과는 [7단계 기록](7/README.md)에 있습니다.
기존 5단계 학습 DB 권한 회수와 커밋 `4f4d313` 배포는 학생 제공 화면으로 확인했습니다.
학생이 본인 메모 CRUD와 상대 메모 거부를 확인했습니다.
원본 API의 공개 키 조회는 401, 공개 키·로그인 토큰 조회와 수정은 모두 403, 시험 전후 메모 비교는 true였습니다.
Supabase Auth 로그인·로그아웃과 개인 메모 읽기·추가·수정·삭제를 제공합니다.
브라우저의 메모 요청은 Vercel `/api/notes` 서버 함수를 사용합니다.
서버는 로그인 토큰과 메모 소유자를 검사합니다. DB에는 authenticated 소유자 RLS가 설정되어 있으며,
anon·authenticated의 테이블·열 직접 권한 회수는 적용 후 조회 화면으로 확인했습니다.
화면에서 공개 키를 제거하고 Auth SDK의 로그인·갱신·로그아웃도 `/api/auth` 서버 함수로 연결했습니다.
기존 브라우저 세션 저장 위치가 바뀌므로 새 배포에서는 다시 로그인합니다.
5단계 미반영·미확인 항목은 [TODO.md](TODO.md)에서 관리합니다.

16단계까지 현재 기능·실행 방법·단계별 목차는 이 README에서 관리합니다.
앞으로 할 목표와 미반영·미확인 항목은 루트 `TODO.md`에만 관리합니다.
각 단계의 `숫자/README.md`에는 완료한 작업의 목표·변경 파일과 이유·실제 적용 및 검증 결과·저장점 커밋을 기록합니다.
코드 작성, DB 적용, 배포, 시험은 각각 수행한 사실만 기록합니다.
미실행 항목은 검증 범위의 한계로 명시하고 후속 할 일은 TODO로 연결합니다.
완료한 목표는 TODO에서 제거하고 해당 단계 기록으로 옮깁니다.
나중에 기능이 바뀌면 현재 README를 갱신하고 새 단계 기록에서 이전 단계와 연결합니다.
프로그램 사본은 단계 폴더에 만들지 않습니다. 실행할 SQL·시험 파일은 기록에서 링크합니다.
비밀값·실명·메모 본문은 기록하지 않습니다.

## 실행과 확인

배포 주소: https://choi-bujang-secret-vault-5.vercel.app

```powershell
npm.cmd run build -- --local
```

이 명령은 정적 빌드 확인입니다. 서버 API·실제 DB·배포 확인을 대신하지 않습니다.
가상 시험은 `node --test test/*.test.mjs`입니다.
서버 환경변수는 Vercel의 **프로젝트 → Settings → Environment Variables** 비밀 입력란에서
`SUPABASE_URL`과 `SUPABASE_SECRET_KEY`를 설정합니다. 값 자체를 코드나 기록에 적지 않습니다.
Auth에는 서버의 기존 키를 사용합니다. 별도 공개 키를 사용하려면 서버 전용 환경변수
`SUPABASE_PUBLISHABLE_KEY`를 같은 비밀 입력란에 설정합니다. 브라우저로 전달하지 않습니다.

DB 적용 순서: Supabase **SQL Editor → New query**에서 [5단계 권한 조회](docs/sql/stage5-library-notes-audit.sql)를 실행해 결과를 보관합니다.
그다음 [권한 회수 SQL](docs/sql/stage5-library-notes-apply.sql)을 검토한 후 전체를 Run하고 같은 조회를 반복합니다.
anon·authenticated 권한은 모두 false, PUBLIC·열 ACL 결과는 없음, 서버용 CRUD는 모두 true여야 합니다.
기존 소유자 정책과 RLS는 유지합니다. 오류 시 `ROLLBACK;` 후 첫 오류를 확인합니다.

배포 화면에서 로그인 후 메모 **추가 → 수정 → 삭제**를 누릅니다.
정상 예상: 본인 메모 CRUD. 거부 예상: 무로그인 401, 상대 메모 읽기·수정·삭제 404,
소유자 변경 본문 400, 기존 ID 덮어쓰기 409. `/data.json`은 404여야 합니다.
실제 DB 적용은 학생이 수행했고 전후 조회 화면을 확인했습니다. 배포 점검과 계정 시험 결과는 5단계 기록에 있습니다.

로컬 설정은 7단계입니다. 기존 배포 주소·Supabase 발급자·메모 API 허용 경로와 `nosniff` 헤더를 유지합니다.
7단계 저장점 `b346b2c` 업로드 뒤 `/aleph.json`의 단계 7·커밋 일치를 실제 HTTP로 확인했습니다.
`originalApiUrl`은 원본 메모 테이블의 쿼리 없는 HTTPS 주소입니다. `judgeIssuer`는 운영 측 설정을 유지합니다.
5단계 당시 배포된 `/aleph.json`의 단계·허용 경로·커밋과 첫 화면 보안 헤더를 실제 HTTP로 확인했습니다.
심판의 `S05_ORIGINAL_URL_MISSING`에 따라 배포 JSON 생성 코드에 원본 주소 출력을 추가했습니다.
공개 화면과 정적 import로 연결된 CDN 파일 10개에서 키·시드 표식 미검출을 확인했습니다.
자동 토큰 갱신과 A에서 B로의 반대 방향 ID 시험은 실제 배포에서 별도 확인하지 않았습니다.
`npm run bundle`은 실제 HTTP 요청에 대한 학생 자기 점검이며 심판 판정이 아닙니다.
`bundle-notes.json`과 `artifacts/submission.json`, 비밀 환경변수, 로컬 보관 자료는 Git에서 제외합니다.
학생의 SQL 확인 캡처 `5/cap/`도 로컬에 보존하고 Git에서 제외합니다.

## 보너스 XDR-01

2026-10-08 수정 요청에 따라 판단을 오프라인 단일 파일로 바꿨습니다.
`xdr/brute-force/decide.mjs` 맨 위에 `patterns.json`의 두 패턴을 그대로 적고,
`decide(alert)` 하나만 내보냅니다. 다른 파일·패키지·인터넷·키·파일 입출력을 사용하지 않습니다.
확신도는 패턴과의 일치 정도이며 0.85 이상 block, 0.5 이상 alert, 그 아래 record입니다.
명확한 근거는 0.95, 정상은 0.1, 부족한 근거는 보조 신호에 따라 0.5~0.83으로 계산합니다.
같은 주소·계정의 단일 실패는 모듈 메모리의 3분 창으로 집계하고 중복 경보·요약 경보는 다시 더하지 않습니다.

`read-alerts.mjs`는 확인용으로 다섯 항목만 출력하며 `decide.mjs`에서 불러오지 않습니다.
`patterns.json`에는 MITRE T1110.001 비밀번호 추측과 T1110.003 비밀번호 스프레이만 있습니다.
`respond.mjs`가 차단 후보의 근거를 다시 확인하여 경보 시각 기준 15분 만료와 근거 경보 번호가 있는
별도 가상 거부 규칙을 만들고 `xdr/alerts.log`에 알림·차단 후보를 한 줄씩 추가합니다.
`connect.mjs`는 이전 호출을 보존하는 재내보내기 파일입니다. 기존 판정 규칙은 수정하지 않았습니다.

프로젝트 루트에서 `npm.cmd run xdr:run -- brute-force`를 실행합니다. Jev 키 설정이 필요 없습니다.
현재 `result.json` counts는 **block 10·alert 9·record 9**, `check.json`의 정상 이벤트·정상 주소 오차단은 각각 0건입니다.
파일 목록에서 **xdr → brute-force → result.json**의 `counts`와 `check.json`의 `fixtureReplay`를 누릅니다.
정상 예상: 정상 이벤트 record, 애매한 시도 alert. 거부 예상: 명확한 공격 block 후보.
가상 허용 판정기에 추가 검사를 연결한 재생은 공격 10건 거부·애매한 9건 통과·정상 9건 통과·만료 규칙 9개 통과입니다.
실제 학생 접속이나 심판의 판정 결과를 확인한 것은 아닙니다.

XDR 제작 당시 `src/decider.mjs`의 starter.deny는 보존했으며, 이후 6단계에서 기기 등록 규칙으로 교체했습니다.
현재 ZTNA 요청 계약에는 출발 IP가 없어
운영 연결에는 검증된 주소 조회·등록된 거부 응답 콜백 계약이 필요합니다. 기본 운영 모드에는 가상 규칙을 적용하지 않습니다.
이전 Jev 웹 시험의 서버·화면·SQL 준비는 로컬의 별도 미커밋 작업으로 보존하며 이번 제출에는 포함하지 않습니다.

## 6단계 기기 등록 규칙과 확인

아래는 6단계 당시 구현·시험 기록입니다. 현재 추가된 조건과 연습 결과는 7단계 안내에서 확인합니다.

`src/decider.mjs`는 엔진이 신원·경로를 확인한 요청에서 `deviceRegistered === true`일 때만
`allow`·`approved`를 반환합니다. 미등록·등록 값 누락은 `deny`·`device_not_registered`이며
실제 구현 규칙 이름은 `device_registered` 하나입니다. 함수·응답 계약은 유지했습니다.
기존 자료실 화면·로그인·메모 API와 XDR 모듈을 변경하지 않았습니다.

프로젝트 루트에서 다음 명령을 실행합니다. 추가 접속 프로그램 설치는 없습니다.

```powershell
npm.cmd run decider:test
```
