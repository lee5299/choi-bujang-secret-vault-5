# XDR-03 제작 1~5 요구사항과 심판 결과 보완

근거: [사용자 요청 원문](xdr-3.txt). 작성: 2026-10-15.
사용자가 지정한 기록 폴더 `XDR-03/`를 사용하고, 실행 모듈은 `xdr/known-cve/`에 둡니다.

## 완료 조건과 자체 점검

- R1: `xdr/fixtures/known-cve.json`을 읽어 시각·출발 주소·계정·규칙 수준·설명 다섯 항목만 추출한다. JSON 한 줄에 경보 한 건을 출력한다.
- R2: 원본은 변경하지 않는다. 실행 전후 SHA-256과 Git 차이를 확인한다.
- R3: URL·User-Agent·원본 로그 등 다른 필드는 반환하지 않는다. 문서용 IP·가상 계정만 허용하고, 비밀값 표식이나 허용하지 않은 문자가 있는 설명은 제외한다. 잘못된 값은 원문 대신 null 또는 제외 표시를 반환한다.
- R4: 확인용 읽기 모듈은 판단 모듈에서 불러오지 않는다. 제작 1에서는 `decide.mjs`를 만들거나 변경하지 않는다.
- R5: 원본 경보 건수와 반환 배열 길이, CLI 표준 출력 줄 수가 모두 일치한다. 누락된 필드가 있어도 경보 행은 버리지 않는다.
- R6: 새 모듈 시험, 기존 XDR 시험, 전체 회귀를 실행하고 가상 시험과 운영 연결·심판 판정을 구분한다.

이전 단계 충돌 점검: ZTNA 판정기·규칙·API·allowedRoutes·step 12 설정과 기존 XDR 모듈은 변경하지 않는다. 원본 24건에 필요한 구조를 확인했다. 제작 5는 아래 사용자 요청 범위로 수행한다.

자체 점검 결과: 문제 없음. 운영 Wazuh 수신·ZTNA 연결·실제 차단·심판 판정은 이번 읽기 제작의 완료 조건이 아니다.

## 제작 2 완료 조건과 자체 점검

근거: [제작 2 사용자 요청](만들기2.txt). 작성: 2026-10-15.

- R7: `xdr/known-cve/patterns.json`에 CVE-2021-44228 관련 머리글·요청 인자의 JNDI 원격 조회와 알려진 취약점 점검 흔적만 정리한다.
- R8: 모든 패턴에 고유한 이름, 찾는 조건, 비어 있지 않은 한 줄 근거와 확인한 공식 출처를 둔다.
- R9: CVE 번호·jndi 단어·중괄호·규칙 수준·도구 비슷한 이름만으로 악용을 확정하지 않는다. 실제 악용 성공과 요청 신호를 구분하고 스캐너 흔적은 보조 신호로 둔다.
- R10: 근거 없는 도구명·다른 CVE·반복 횟수·시간·차단 임계값은 추가하지 않는다. 읽기 모듈과 원본·기존 판단 규칙을 보존한다.

자체 점검 결과: 문제 없음. Apache 공식 CVE 설명과 MITRE T1190·T1595.002를 확인했다. 머리글·인자 구분은 사용자 요청과 수업 경보 구조에 따른 분리이며, 스캔과 악용을 같은 판정으로 합치지 않는다. 이번에는 목록만 작성하며 판단 코드는 제작하지 않는다.

## 제작 3 완료 조건과 자체 점검

근거: [제작 3 사용자 요청](만들기3.txt). 작성: 2026-10-15.

- R11: patterns.json의 세 패턴 전체를 decide.mjs 맨 위 상수로 복사한다. 파일 읽기·네트워크·키 없이 동기 decide(alert) 하나만 내보낸다.
- R12: 반환 항목은 action·confidence·reason 세 개다. 확신도는 유한한 0~1 숫자이며 0.85 이상 block, 0.5 이상 alert, 미만 record로 계산한다.
- R13: 완전한 JNDI 외부 조회는 0.95, 위치와 조회 존재를 명시한 수업 설명만 있으면 0.75, 잘린 구문 또는 명확한 점검 흔적만 있으면 0.6이다. 요청 인자·머리글의 CVE 이름·jndi 단어만은 후보 신호 0.5이며 block으로 승격하지 않는다. 높은 수준·반복 수만으로 승격하지 않는다. 근거 없음은 0.1, 잘못된 최상위 입력은 0이다. 점수는 이 구현의 연습 기준이며 공식 확률이 아니다.
- R14: reason은 내장 패턴 이름 한 줄이며 입력 원문을 복사하지 않는다. 근거 패턴이 없는 record에는 상태 표시 no_matching_pattern을 사용한다. 이는 추가 탐지 패턴이 아니다.
- R15: 원본·입력을 변경하지 않고 반복 호출 순서에 의존하지 않는다. 수업 경보 전체, 정상·불완전 구문·점검 흔적, 인코딩·잘못된 입력과 단일 파일 격리 시험을 수행한다.

자체 점검 결과: 문제 없음. 머리글과 URL 인자만 검사하고 다른 필드의 공격 문자열을 끌어오지 않는다. 난독화 전체를 해석하는 범용 탐지기는 만들지 않는다. 제작 4의 운영 연결·차단 집행은 구현하지 않는다.

## 제작 4 완료 조건과 자체 점검

근거: [제작 4 사용자 요청](만들기4.txt). 작성: 2026-10-15.

- R16: respond.mjs가 제출된 block 후보를 원본 경보의 decide 결과와 대조한 뒤에만 별도 deny-rules.json을 만든다. 위조 점수·이유·경보 번호·중복 번호는 규칙에 쓰지 않는다.
- R17: 규칙은 moduleKey·fixture 모드·문서용 주소·시작 시각·경보 시각 기준 15분 만료·안전한 근거 경보 번호·패턴 이름을 가진다. 재실행으로 만료를 현재 시각까지 연장하지 않는다.
- R18: 차단 시간대에 같은 주소를 쓰는 비차단 사건이 있으면 주소 차단을 제외한다. 정상·애매한 사건·만료된 규칙·시작 전 요청이 가상 재생에서 통과해야 한다.
- R19: 알림은 원본과 재검증한 alert/block 결과에 한해 안전한 메타데이터만 xdr/alerts.log에 JSON 한 줄씩 누적한다. 기존 로그와 다른 모듈 결과를 보존한다.
- R20: 추가 검사 부품은 기존 판정부터 실행해 deny·step_up을 그대로 유지한다. 주소는 공식 검증 함수에서만 받으며 request에 IP 필드를 만들지 않는다. 가상 규칙은 기본 live 모드에서 사용하지 않는다. 새 deny 응답은 다섯 항목 계약을 검증한다.
- R21: 공통 실행기에 known-cve 응답 연결을 추가하고 임시 복제본에서 실제 파일 쓰기·알림 누적·재생을 시험한다. 기존 src/decider.mjs 및 known-cve/decide.mjs는 변경하지 않는다. 관련 시험·전체 회귀·보안 검토를 구분해 보고한다.

자체 점검 결과: 로컬 추가 검사·가상 재생 구현은 가능하다. 현재 DECIDER_REQUEST 계약에는 출발 주소가 없고 운영용 거부 응답 코드 등록도 확인되지 않아 실제 운영 연결은 미완료로 남긴다. 가상 규칙을 운영에 연결하거나 기존 규칙을 바꾸는 방식으로 이 경계를 우회하지 않는다. 관찰되지 않은 미래의 정상 사용자까지 IP 주소만으로 식별할 수 없으므로 정상 보존 검증은 제공된 사건과 재생 범위에 한정한다.

## 제작 5 완료 조건과 자체 점검

근거: [제작 5 사용자 요청](만들기5.txt). 작성: 2026-10-15.

- R22: npm.cmd run xdr:run -- known-cve를 실제로 실행하고 result.json의 counts 합계가 원본 24건 및 decisions 길이와 같은지 확인한다.
- R23: 정상 기대 사례는 판단 결과로 다시 고르지 않고, 원본의 공개 화면·상태 확인·로그인 성공·정적 파일·본인 메모·세션 유지·공지 조회·로그아웃인 kc-17~kc-24 여덟 건으로 따로 확인한다. 이 여덟 건이 모두 record이고 block이 0건이어야 한다. 명확한 공격이 아닌 kc-09~kc-24 전체에도 block이 없어야 한다.
- R24: check.json의 normalBlocked와 normalAddressBlocked가 0이고, 가상 요청을 다시 흘렸을 때 정상·애매한 요청이 통과하는지 함께 확인한다. check.json의 normalEventCount는 판단 코드가 record로 분류한 건수이며 위 정상 기대 사례 여덟 건과 구분한다.
- R25: 정상 오차단이 발견됐을 때만 해당 경보 한 건을 골라 원인을 수정한다. 없다면 기존 판단 코드를 바꾸지 않는다. 기존 알림은 보존하고 이번 실행의 알림만 추가한다. 관련 시험과 전체 시험을 실행한다.

자체 점검 결과: 문제 없음. 이전 제작의 실행 결과를 이번 실행 결과로 재사용하지 않고 새로 실행해 확인한다. 운영 연결·배포·GitHub 업로드·심판 제출은 이번 요청에 포함되지 않는다.

## 심판 결과에 따른 분류 보완 (2026-10-15)

사용자 보고: `X03_AMBIGUOUS_NOT_ALERT` — 「애매한 시도가 알림이 아니거나, 알림 건수가 정답표와 다릅니다.」 및 「정상 이벤트를 막지는 않았지만 기록 건수가 정답표와 다릅니다.」 점수·정상 기록 오류 코드는 제공되지 않았습니다.

- R26: 기존에는 record였던 취약점 목록 조회·머리글 중괄호 흔적·비슷한 점검 도구 이름·라이브러리 이름을 확신도 0.5의 alert로 분류한다. 명확한 구문이 없으므로 block으로 올리지 않는다.
- R27: 기존 명확한 공격 8건은 block, 애매한 시도 8건은 alert, 일반 정상 8건은 record로 기대하는 시험을 먼저 실패시킨 뒤 수정한다. 이 건수는 로컬 경보에서 확인할 기대값이며 공식 정답표를 직접 받은 것은 아니다.
- R28: 실행 코드 변경은 decide.mjs의 확신도 분기에 한정한다. 내장 패턴·함수 형식·문자열 해석·respond.mjs·기존 ZTNA 규칙·원본을 보존한다. 관련 시험의 기존 4/12 집계는 이번 8/8 기대값으로 갱신한다.
- R29: 실행기로 결과를 다시 만들고 정상 차단 0건과 기존 공격 거부·만료 동작을 확인한다. 새 커밋·업로드·심판 재제출은 이번 수정 요청에 포함되지 않으며 사용자가 최종 제출 버튼을 직접 누르는 지시를 유지한다.

자체 점검: 기존 시험은 애매한 사건이 block이 아닌지만 검사해 record로 내려간 오류를 놓쳤다. alert를 정확히 요구하도록 보완한다. 다른 1~12단계 시험의 기대값은 바꾸지 않는다. 이번 실패는 단일 파일의 경보 분류에 대한 사용자 보고이며 Vercel HTTP 요청 로그는 이번 수정에서 조회하지 않았다.
