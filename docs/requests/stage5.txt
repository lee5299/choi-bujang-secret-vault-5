5단계: 자료 요청을 서버 한곳으로 모읍니다
========================================

이 문서는 작업 요청입니다. 완료 결과는 5/README.md에 기록합니다.
각 제작 요청은 한 번에 하나씩 진행합니다.

1. 지금 상황
------------
브라우저의 메모 요청은 서버 함수를 사용하고 있지만, 로그인한 사용자의
토큰으로 Supabase 자료 저장소를 직접 호출할 수 있는 권한이 남아 있습니다.
이번 단계에서는 이 직접 접근 경로를 닫습니다.

2. 목표와 만들 방어 도구
-----------------------
브라우저의 메모 읽기·추가·수정·삭제는 Vercel 서버 함수를 통해서만 처리합니다.
학습용 메모 테이블의 PUBLIC·anon·authenticated 직접 접근 권한을 회수합니다.
공개 키만 사용하거나 공개 키와 로그인 토큰을 함께 사용하는 직접 요청을 차단합니다.
서버 함수의 로그인·소유자 검사와 서버 전용 설정은 유지합니다.
A와 B의 본인 메모 처리는 정상 동작해야 합니다.
기존 메모, 다른 테이블과 다른 기능은 보존합니다.

3. 점수 기준
------------
[기본 조건: 모두 방어 성공 시 70점]

검사 1: 공개 키와 시험 계정 토큰으로 원본 Supabase 자료 API 직접 조회
성공 조건: 메모가 반환되지 않습니다.

검사 2: 공개 키와 시험 계정 토큰으로 원본 Supabase 자료 API 직접 수정
성공 조건: 수정 요청이 거부되고 기존 메모가 변경되지 않습니다.

검사 3: 공개 정적 파일과 브라우저 묶음에서 서버 전용 키·시드 표식 검색
성공 조건: 서버 전용 키와 시드 표식이 발견되지 않습니다.

[추가 조건: 기본 조건 통과 후 각 10점]

1) 배포된 /aleph.json의 allowedRoutes에 실제 허용 경로가 하나 이상 있습니다.
2) 첫 화면 응답에 보안 헤더가 있습니다.
   vercel.json의 headers에 X-Content-Type-Options: nosniff
   또는 Content-Security-Policy를 설정합니다.
3) 화면 코드와 브라우저에 전달되는 파일·설정·응답에 Supabase 공개 키가 없습니다.
   sb_publishable_… 또는 anon 키는 서버 함수에서만 사용합니다.

추가 조건 세 가지를 모두 충족하면 100점입니다.
재제출 시 가장 높은 점수가 유지됩니다.

4. 작업 기록 관리
-----------------
프로그램 코드·설정·계약 문서는 기존 실행 위치에서 관리합니다.

README.md                 현재 기능·실행 방법·단계별 기록 목차
TODO.md                   미완료 목표·미반영·미확인 사항
docs/requests/stage5.txt   이번 작업 요청
5/README.md               이번 단계에서 완료한 작업과 실제 검증 결과

단계당 작업 기록 파일은 하나로 유지합니다.
기록에는 변경 파일과 이유, 실제 적용·검증 결과, 저장점 커밋을 남깁니다.
실행용 SQL·시험 코드는 별도 파일로 두고 기록에서 링크합니다.
단계 폴더에 프로그램 사본을 만들지 않습니다.
비밀번호·토큰·키·실명·메모 본문은 기록이나 제출 묶음에 넣지 않습니다.

5. 이어받기: 읽기만 수행
-----------------------
이 프로젝트는 1~4단계에서 이어온 같은 자료실이야.
이번에는 5단계 「자료 요청을 서버 한곳으로 모읍니다」를 진행할 거야.

AGENTS.md, README.md, 폴더 구조, git status, git log -1을 확인해 줘.
README의 단계 기록과 마지막 커밋이 일치하는지 대조하고,
어긋나면 먼저 알려 줘. 현재 기능을 다섯 줄 이내로 요약해 줘.
다른 작업은 보존하고, 이 확인 단계에서는 파일을 수정하지 마.

6. 제작 1: 브라우저의 직접 메모 호출 확인
----------------------------------------
브라우저 코드에 Supabase 메모 테이블을 직접 읽거나
추가·수정·삭제하는 호출이 있는지 찾아 줘.

있으면 기존 Vercel 서버 함수 호출로 바꿔 줘.
로그인(Auth) 호출은 이번 제작에서 유지해.
직접 메모 호출이 없으면 '없음'이라고만 답하고 아무 파일도 수정하지 마.

확인 기준:
- 직접 메모 호출이 있었다면 서버 함수 호출로 변경되어야 합니다.
- 없었다면 파일 변경이 없어야 합니다.

7. 제작 2: DB 직접 접근 권한 회수 준비
-------------------------------------
먼저 서버 함수의 메모 읽기·추가·수정·삭제 구현과
로그인·소유자 검사를 확인해 줘.
코드 확인, 가상 시험, 실제 A 계정 시험 결과는 구분해서 기록해 줘.

학습용 public.library_notes 테이블만 대상으로
PUBLIC·anon·authenticated의 직접 접근 권한을 회수하는 SQL 한 묶음과
적용 전후 권한 조회 SQL을 준비해 줘.
열 단위 권한이나 상속된 권한이 남는지도 확인해 줘.

다른 테이블, 메모 행, 서버용 역할의 권한,
기존 로그인·소유자 검사는 변경하지 마.
SQL은 내가 검토한 뒤 학습 DB에서 실행할게.

쿼리 문자열이 없는 원본 메모 API의 HTTPS 주소를
aleph.config.json의 originalApiUrl에 기록해 줘.

확인 기준:
- 권한 회수 뒤에도 A와 B의 본인 메모 CRUD는 서버 함수에서 정상 동작합니다.
- 공개 키만 사용한 원본 직접 요청에서 메모가 반환되지 않습니다.
- 공개 키와 시험 계정 토큰을 함께 사용한 직접 조회·수정도 거부됩니다.
- 직접 수정 요청 후 기존 메모가 변경되지 않습니다.

8. 추가 점수 작업: 세 조건 구현·확인
-----------------------------------
아래는 원래 제작 1·2와 구분하는 추가 점수 작업입니다.
'제작 3'이라는 별도 원문 단계로 취급하지 않습니다.

[허용 경로]
실제 서버 API 경로와 aleph.config.json의 allowedRoutes를 대조해 줘.
배포된 /aleph.json에도 허용 경로가 하나 이상 있는지 확인해 줘.

[보안 헤더]
vercel.json의 headers에 nosniff 또는 Content-Security-Policy가 있는지
확인하고, 없으면 설정해 줘. 배포된 첫 화면 응답에도 붙는지 확인해 줘.

[화면 공개 키 제거]
현재 로그인(Auth)이 브라우저의 Supabase 공개 키에 의존하는지 확인해 줘.
의존한다면 로그인·로그아웃과 기존 서버 토큰 검증을 유지하면서
필요한 Auth 처리를 서버 함수로 옮겨 줘.
제작 1에서 Auth를 유지하는 범위와 구분해서 진행해 줘.
공개 키를 내려주는 설정 API로 우회하지 마.
화면 코드와 브라우저에 전달되는 파일·설정·응답에 공개 키가 없는지 확인해 줘.
비밀번호·토큰·키를 코드, 로그, 작업 기록에 남기지 마.

9. 직접 확인할 것: 구현과 학습 DB SQL 적용 후
--------------------------------------------
기존 세 항목을 중심으로 아래 세부 점검을 함께 진행합니다.

1) 브라우저의 메모 요청은 서버 함수만 부르는가?
   - 메모 읽기·추가·수정·삭제가 모두 Vercel 서버 함수를 사용하는지 확인합니다.

2) A 정상·B 거부·무로그인을 확인했는가?
   - A의 본인 메모 읽기·추가·수정·삭제가 정상 동작하는지 확인합니다.
   - B가 A의 메모를 읽거나 수정·삭제하려 하면 거부되는지 확인합니다.
   - A가 B의 메모에 접근해도 거부되는지 함께 확인합니다.
   - B의 본인 메모는 정상 처리되는지도 확인합니다.
   - 무로그인 메모 요청이 거부되는지 확인합니다.

3) 원본 자료 주소를 공개 키로 직접 불러도 메모가 없는가?
   - 공개 키만 사용한 직접 요청에서 메모가 반환되지 않는지 확인합니다.
   - 공개 키와 시험 계정 토큰을 함께 사용한 직접 조회·수정도 거부되는지 확인합니다.
   - 직접 수정 요청 후 기존 메모가 변경되지 않았는지 확인합니다.

별도로 함께 확인할 점수 항목:
- 기본 조건: 공개 정적 파일·브라우저 묶음의 서버 전용 키·시드 표식 미노출.
- 추가 조건: 허용 경로 등록, 첫 화면 보안 헤더, 화면 공개 키 제거.

시험에는 공개 가능한 가상 메모만 사용합니다.
미실행·미확인 항목은 그대로 기록합니다.
학생 자기 점검 결과를 운영 심판의 판정으로 표현하지 않습니다.

10. 5단계 저장점: 적용과 확인 후 별도 요청
-----------------------------------------
SQL 적용과 실제 확인 결과를 기록한 뒤 저장점을 진행해 줘.
미실행·미확인 항목은 완료로 기록하지 마.

완료한 작업과 검증 결과를 5/README.md에 정리하고,
루트 README.md와 TODO.md를 현재 상태에 맞춰 갱신해 줘.

aleph.config.json의 단계·배포 주소·로그인 발급자·허용 경로·원본 API 주소를
구현과 대조해 줘. judgeIssuer는 변경하지 마.

커밋 전에 포함할 파일과 비밀값 검사 결과를 보여 줘.
다른 작업은 제외하고 이번 변경만 '5단계 저장점'으로 커밋해 줘.

그다음 npm run bundle을 실행하고 제출 묶음 JSON과 요약을 보여 줘.
자기 점검에는 실제로 보낸 요청 결과만 기록해 줘.
비밀값·실명·메모 본문은 포함하지 마.
bundle-notes.json과 artifacts/submission.json은 커밋하지 마.

오류가 나면 첫 오류를 근거로 필요한 한 가지 수정만 하고 다시 실행해 줘.
실제로 실행하지 않은 명령·시험·배포는 완료했다고 말하지 마.
