# 요구사항 정리와 점검

트리거: 새 단계 안내 원문을 받은 뒤 **제작 1을 시작하기 전**. 「요구사항 정리」, 「요구사항 검토」 요청.
목적: 안내 원문과 현재 계약으로 요청·기대 결과·구역·허용 경로·이전 단계 충돌을 코드 작성 전에 표로 고정합니다. 과거 기록은 구현과 확인 범위를 대조하는 보조 근거이며 새 단계의 공식 명세를 대신하지 않습니다.

## 1. 정리

`N/요구사항.md`를 아래 형식으로 만듭니다. 안내 원문의 문장을 근거로 붙이고, 원문에 없는 것은 「추정」으로 표시합니다.

```markdown
# N단계 요구사항 표

근거: [안내 원문](../docs/requests/stageN.txt) · 작성 YYYY-MM-DD

## 심판 요청 표
| # | 출처(원문 문장) | 누가 | service·method·경로 | 기대 판정 | 사유 코드 | 규칙 이름 | API 기대 응답 |
| - | --- | --- | --- | --- | --- | --- | --- |
| M1 | 괴물: 다른 구역 메모 조회 | B | notes GET /notes/:id(A) | allow(판정기는 주인 모름) | — | resource_scope | 404 not_found_or_not_owner |
| N1 | 직접 확인: 본인 정상 요청 | A | notes GET /notes/:id | allow | approved | resource_scope | 200 |

## 구역 표
| 구역 | service | 경로(접두사 /api 유무 모두) | 허용 동작 | 거부 사유 코드 | 규칙 이름(RULE_IDS) |

## allowedRoutes 후보
판정기가 허용하는 경로와 정확히 같은 목록.

## 이전 단계와의 충돌 점검
| 단계 | 기존 기대(시험 파일) | 이번 변경 영향 | 결론 |

## 제작별 완료 조건
| 작업 | 원문 근거 | 완료 조건 | 추천 방향 |

## 미확정·질문
원문만으로 정할 수 없는 것. 추측으로 구현하지 않고 질문 게시판에 물을 후보.
```

작성 규칙:
- 「이번 단계에 들어오는 괴물」 하나마다 최소 한 행(거부), 「직접 확인할 것」의 정상 요청마다 최소 한 행(허용).
- 막는 범주마다 **이름 붙은 구역 + 전용 사유 코드 + RULE_IDS 규칙 이름**을 정합니다. 「모르는 경로라서 막힘」으로 두지 않습니다.
- 사유 코드는 소문자·밑줄의 짧은 코드(예: `announcement_write_denied`). 기존 `approved`·`device_not_registered`·`step_up_required`의 의미를 바꾸지 않습니다.
- 계약(`docs/DECIDER_REQUEST.md`)에 없는 값(역할·소유자 등)이 필요하면 판정기가 아니라 자료 API 쪽 행으로 옮깁니다.

## 2. 요구사항 점검

현재 작업자가 아래 항목을 점검하고 필요한 내용을 요구사항 표에 반영합니다. 다른 도구의 검토·협업·재승인을 제작 시작 조건으로 두지 않습니다. 사용자가 별도로 검토를 요청하면 그 요청 범위에서 진행합니다.

| 점검 항목 | 확인 내용 |
| --- | --- |
| 누락 | 괴물·직접 확인 문장이 모두 표의 행으로 있는가. 원문에 나온 자료 종류(예: 강사 자료)마다 구역이 있는가 |
| 심판 환경 | 환경변수·권한표·외부 설정 없이 표의 기대 판정이 나오는가. ID가 UUID가 아니거나 `/api` 없는 경로로 와도 같은가 |
| 여러 사람 자료 | 전체 목록·검색·export처럼 여러 사람의 자료를 한꺼번에 여는 경로를 허용하지 않는가 |
| 역할 의존 | 계약에 없는 역할·소유자를 판정기에서 가정하지 않는가 (그런 판단은 API 행으로) |
| 이전 단계 | 기존 시험(`test/decider-stage*.test.mjs` 등)의 기대값을 뒤집는 행이 없는가. 있으면 충돌 표에 결론이 있는가 |
| 신고 경로 | allowedRoutes 후보가 판정기 허용 경로와 정확히 같은가 |
| 사유·규칙 | 거부 행마다 사유 코드와 RULE_IDS 규칙 이름이 있는가 |

검토 결과는 「문제 없음 / 수정 필요(행 번호와 이유) / 질문 필요」 중 하나로 끝냅니다.
수정 필요 항목은 요구사항 표에 반영하고 중요한 판단 이유를 같은 파일에 기록합니다.
**요구사항 정리와 자체 점검이 끝나면 요청받은 제작을 시작합니다.** 미확정·질문 항목은 제작을 막지 않고 미연결·미확인으로 표시합니다.

## 3. 표를 시험으로

제작 중 `test/rN-requirements.test.mjs`에 표의 각 행을 그대로 시험으로 옮깁니다 (행 번호를 시험 이름에 포함).
환경변수 `ALEPH_RESOURCE_POLICY_JSON`을 지운 상태에서 실행하고, allowedRoutes와 판정기 허용 경로의 일치도 시험합니다.
