## 제작 4: 알림 저장과 추가 차단 검사 (2026-10-15)

근거는 [제작 4 사용자 요청](../../XDR-03/만들기4.txt)입니다. `respond.mjs`는 판단 결과를 받아 원본 경보로 다시 계산한 결과와 대조합니다. 경보 번호·행동·점수·패턴 이름이 일치한 block 후보만 `deny-rules.json`에 넣습니다. 중복 번호, 원본에 없는 번호, 임의로 높인 점수나 바꾼 이유는 채택하지 않습니다.

규칙에는 `moduleKey: known-cve`, `mode: fixture`, 문서용 IP, 시작 시각, 경보 시각부터 15분 뒤의 만료 시각, 근거 경보 번호, 패턴 이름을 저장합니다. 같은 시험을 다시 실행해도 현재 시각을 기준으로 만료를 연장하지 않습니다. 규칙은 시작 시각에 적용되고 만료 시각부터 적용되지 않습니다.

정상 사용자 보호: 같은 주소에서 차단 시간대에 정상 또는 애매한 사건이 관찰되면 해당 후보의 주소 차단 규칙은 제외합니다. 같은 주소의 비차단 사건에 시각이 없어도 규칙을 제외합니다. 다만 관찰하지 못한 미래의 정상 요청까지 주소만으로 구별할 수는 없습니다. 이번 확인은 제공된 사건과 추가 시험의 범위에 한정합니다.

### 기존 판정기에 붙이는 부분

`withXdrCheck`는 먼저 기존 판정 함수를 실행합니다. 기존 결과가 deny 또는 step_up이면 그 객체를 그대로 반환합니다. 기존 결과가 allow인 가상 요청에 대해서만 별도 차단 규칙을 확인합니다. 규칙이 없으면 기존 응답을 그대로 반환하고, 있으면 호출 측이 제공한 거부 응답이 다섯 항목 형식에 맞는지 검사합니다.

주소는 요청에 임의 필드를 추가해 받지 않고, 호출 측이 출처를 확인하는 함수 `verifiedSource`에서 받도록 했습니다. 현재 ZTNA가 판정기에 보내는 정보에는 출발 IP가 없으므로 실제 운영 연결은 하지 않았습니다. 이 파일이 만드는 규칙은 가상 시험 전용이며, 기본값인 live 모드에서는 규칙·주소 조회 함수를 호출하지 않습니다. 저장 파일의 mode만 live로 바꿔도 적용되지 않습니다. 실제 운영 연결에는 주소 확인 방법과 운영자가 허용한 거부 이유 코드가 별도로 필요합니다.

`replayFixture`는 가상으로 허용하는 판정 함수에 이 추가 검사를 붙여 시험 경보를 다시 흘립니다. 이는 실제 ZTNA가 정상 접속을 허용하거나 공격 접속을 막았다는 증거가 아닙니다. 별도 시험에서는 기존 `src/decider.mjs`의 기기 미등록 거부·추가 인증 요구·정상 허용 결과가 보존되는지도 확인했습니다.

### 알림과 파일 저장

`applyRun({root, alerts, result})`가 규칙과 확인 결과를 저장합니다. 원본과 대조한 block·alert 결과만 `xdr/alerts.log` 끝에 JSON 한 줄씩 추가합니다. 기록 항목은 모듈 이름·fixture 표시·경보 번호·행동·점수·패턴 이름뿐입니다. 주소·계정·요청 원문·비밀값은 알림에 복사하지 않습니다. 가상 규칙 파일의 주소는 문서용 주소만 허용합니다.

공통 실행기 `scripts/xdr-run.mjs`의 응답 모듈 호출 대상에 `known-cve`를 추가했습니다. 기존 두 모듈의 동작은 유지했으며 [절차 원본](../../docs/workflows/xdr-module.md)의 현재 호출 대상 설명도 맞췄습니다. 이번 작업에서 `decide.mjs`와 기존 ZTNA 규칙은 수정하지 않았습니다.
